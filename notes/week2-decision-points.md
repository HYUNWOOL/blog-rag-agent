# 2주차 결정 포인트 (미결정)

정하면 `notes/decisions.md`에 남긴다. API 근거는 `notes/week2-api.md`.

그래프 흐름 가정: `rewrite_query → retrieve → grade → answer`, 부족하면 다시 `rewrite_query`, 상한에 닿으면 `insufficient`.

1주차 결정 C(기본 v0, 멀티홉만 에이전트)와의 관계: 이 그래프에서는 라우터가 따로 필요 없다. 첫 검색으로 충분하면 v0처럼 끝나고, 부족할 때만 루프가 돈다. 대신 `grade`가 모든 질문에 붙으므로 그 비용이 v0보다 늘어난다.

## 1. State 필드

정할 것: 노드끼리 무엇을 주고받고, 체크포인트에 무엇을 남길지.

| 선택지 | 필드 | 장점 | 단점 |
| --- | --- | --- | --- |
| A. messages 중심 | messages(add_messages), llm_calls | 1주차 그래프와 같은 모양 | 검색어·청크·판정을 메시지에서 꺼내야 해서 노드와 테스트가 복잡 |
| B. 명시 필드 | question, query, chunks, attempts, verdict, answer, llm_calls | 노드 입출력이 분명하고 `get_state`로 바로 읽힘. 가짜 값으로 노드 단위 테스트가 쉬움 | 대화 이력이 필요해지면 필드를 더해야 함. chunks가 체크포인트마다 저장됨(청크 5개 약 2.5천 자) |
| C. B + messages | B에 messages 추가 | 멀티턴 대화까지 대비 | 이번 주 범위에 쓰지 않는 필드. 같은 내용이 두 곳에 남음 |

추천: **B**. 이번 주 범위는 단일 질문이고, kill 실험에서 `get_state`로 어디까지 갔는지 바로 읽는 데 유리하다. attempts는 리듀서 없이 노드가 +1 해서 돌려준다.

## 2. 충분성 판단

정할 것: 찾은 청크로 답할 수 있는지 무엇으로 정할지.

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| A. LLM 판정(구조화 출력) | "일부만 있음"을 알아챌 수 있고, 무엇이 부족한지 다음 검색어에 쓸 수 있음 | LLM 호출이 질문마다 1번 는다. 판정 프롬프트와 평가가 필요. 입력 청크가 v0와 같다면 질문당 약 $0.0003 추가(추정, 미측정) |
| B. 검색 점수 임계값 | 비용 0, 결정적, 빠름 | 아래 1주차 숫자로는 기준선을 긋기 어렵다 |
| C. 점수로 1차 거름 + LLM 판정 | 명백히 먼 결과는 LLM 없이 바로 재검색 | 분기와 튜닝값이 둘 다 생긴다 |

1주차 근거: 맞는 청크의 1위 거리가 0.249~0.471까지 있고, 블로그에 없는 파리 질문의 1위가 0.492였다. 차이가 0.02뿐이라 임계값이 불안정하다. 또 9번(튀르키예 순서)은 1위 거리 0.423으로 좋아 보이지만 정보가 부족했다. **거리는 "관련 있음"은 말해도 "충분함"은 말하지 못한다.**

추천: **A**. 멀티홉을 잡는 것이 이 그래프의 이유이고, 점수로는 그걸 못 잡는다. 비용은 2주차 평가에서 측정한다.

## 3. 재검색 상한과 상한에 닿았을 때의 행동

정할 것: 재검색을 몇 번 허용하고, 그래도 부족하면 어떻게 끝낼지.

상한 횟수: 1주차 9번은 검색 2번이면 충분했다. 재검색 2번(총 검색 3번)을 제안한다. 이때 super-step은 최대 10개(`rewrite·retrieve·grade` 3회 + 마지막 노드)라 **1주차의 `recursion_limit=10`으로는 빠듯하다.** 15 정도로 올려야 한다.

| 상한 도달 시 행동 | 장점 | 단점 |
| --- | --- | --- |
| A. 안내(`insufficient` 노드) | 항상 바로 끝남. 체크포인트 없이도 동작. 지금까지 찾은 글을 함께 보여 줄 수 있음 | 사용자가 다시 물어야 함 |
| B. `interrupt`로 되묻기 | "어느 도시 말씀인가요?"처럼 사람 입력으로 검색을 살릴 수 있음 | 대기 상태를 다룰 API·화면이 필요. 재개 때 노드가 다시 돌아 앞쪽 코드의 멱등성도 챙겨야 함 |
| C. A 후 그래프 밖에서 재질문 | 대화형 UI에서 자연스러움 | 멀티턴을 다뤄야 해서 이번 주 범위를 넘음 |

추천: **A**. 아직 웹 화면이 없어서 interrupt를 받아 줄 쪽이 없다. 화면이 생긴 뒤 B를 더해도 그래프 구조는 크게 바뀌지 않는다.

## 4. 질문 로그의 멱등 방법

정할 것: 재시도나 kill 뒤 재개로 노드가 다시 돌아도 로그가 한 번만 남게 하는 방법.

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| A. 멱등키 upsert | DB 제약이 보장하므로 재시도·재개·동시 실행 어디서든 안전. SQL로 바로 검증 가능 | 키 설계가 필요. 예: `UNIQUE(thread_id, turn)` + `ON CONFLICT` |
| B. `@task`로 감싸기 | 완료된 task 결과는 재개 때 재사용되어 코드가 짧음 | INSERT 커밋 뒤 결과가 저장되기 전에 죽으면 다시 실행된다. 정확히 한 번을 보장하지 못하고, 그때 INSERT면 중복 |
| C. 그래프 밖에서 기록 | 그래프가 끝난 뒤 한 번만 쓰므로 단순 | 도중에 죽은 질문은 로그에 남지 않음 |

추천: **A**. 문서도 재실행 대비로 멱등키와 upsert를 권한다. kill 실험으로 "두 번 돌아도 1행"을 테스트할 수 있다. 테이블은 Alembic 마이그레이션으로 만든다.

## 5. 체크포인터 테이블과 "스키마는 Alembic으로만" 규칙 (추가)

요청 목록에는 없지만 CLAUDE.md 규칙과 충돌해서 넣었다. `setup()`이 직접 DDL을 실행하고, 그중 `CREATE INDEX CONCURRENTLY`는 트랜잭션 안에서 실패하므로 Alembic 마이그레이션에 그대로 넣을 수 없다.

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| A. 규칙에 예외를 명시하고 전용 스크립트로 `setup()` 실행 | 라이브러리가 관리하는 테이블이라 업그레이드가 안전 | 규칙에 예외가 하나 생김 |
| B. Alembic에서 autocommit 블록으로 `setup()` 호출 | 명령 하나로 전부 적용 | 라이브러리 버전 업과 Alembic 이력이 어긋날 수 있고, downgrade를 직접 써야 함 |
| C. DDL을 Alembic에 복사 | 규칙을 그대로 지킴 | 라이브러리 스키마를 손으로 따라가야 해서 깨지기 쉬움 |

추천: **A**. 함께 해야 할 일: `tests/conftest.py`의 테이블 비우기가 `checkpoint_migrations`까지 지우지 않도록 제외한다.

## 6. 노드를 async로 할지 (추가)

타임아웃을 만들려면 필요한 결정이다. 노드 `timeout=`은 async 노드에서만 동작한다.

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| A. async 노드 + AsyncPostgresSaver | `timeout=`을 쓸 수 있고, 나중 FastAPI와 잘 맞음 | Windows에서 셀렉터 이벤트 루프 설정 필요. `search`·임베딩이 동기라 이벤트 루프를 막지 않게 처리해야 함 |
| B. 동기 노드 + 클라이언트 타임아웃 | 코드가 단순. LLM·DB 클라이언트 자체 타임아웃으로 대부분 해결 | `NodeTimeoutError`와 `TimeoutPolicy`를 쓰지 못함 |

추천: **A**. 이번 주 목표에 타임아웃이 있고 서버도 곧 async로 간다. 다만 kill 실험 도구는 지금 동기로 만들었고, 그래프가 async가 되면 그때 맞춘다.
