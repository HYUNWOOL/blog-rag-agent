# 3주차 결정 포인트 (미결정)

정하면 `notes/decisions.md`에 남긴다.

3주차 목표: 2주차에서 넘긴 멀티홉 답변 품질(튀르키예 이동 순서)을 질문 하나가 아니라 평가셋으로 잰다. 그 숫자를 보고 판정 기준과 재검색(찾은 글 제목 전달 등)을 다시 정한다.

재료: 글 33편. 여러 글을 이어야 하는 묶음이 있다. 튀르키예 5편(카파도키아 → 안탈리아 → 파묵칼레 → 부르사·이스탄불), 노르웨이 6편(오슬로 2, 베르겐 2, 트롬쇠 2), 밴쿠버 3편, 밴프 2편, 하노이·사파·나트랑 4편, 스페인 4편(세비야 2, 론다, 말라가).

## 1. 평가셋 구성

정할 것: 질문을 몇 개, 어떤 종류로, 누가 만들지. 정답은 어떤 모양으로 둘지.

| 선택지 | 내용 | 장점 | 단점 |
| --- | --- | --- | --- |
| A. 손으로 24개 | 단일 글 8, 멀티홉 10, 블로그에 없음 3, 후속 질문(두 턴) 3. AI가 글을 읽고 초안을 쓰고, 사용자가 정답을 검수 | 질문마다 왜 넣었는지 설명할 수 있음. 검수 부담이 작음 | 통계로 보기엔 적다. 1문항이 4%p |
| B. LLM 생성 60개 | 글마다 LLM이 질문과 정답을 만들고 일부만 검수 | 수가 많아 비교가 안정적 | 생성 질문이 한 글짜리로 쏠리기 쉽고, 검수 안 한 정답이 틀릴 수 있음 |
| C. 1주차 10개 + 멀티홉 10개 | 기존 질문을 그대로 살림 | 1주차 숫자와 이어 비교 가능 | 쉬운 질문 비중이 높고 후속 질문이 없음 |

정답 모양(모든 선택지 공통 제안): 질문마다 `type`, 정답 글 slug 목록, 답에 꼭 들어가야 하는 사실 목록(한 줄에 사실 하나), 순서가 중요하면 `ordered: true`. 블로그에 없는 질문은 "없다고 답해야 함"으로 둔다. 파일은 `BE/experiments/week3/evalset.jsonl`.

추천: **A**. 이번 주 질문은 "멀티홉을 고치면 나아지나"라서 멀티홉 비중이 높고 정답이 확실한 쪽이 낫다. 1주차 10개 중 쓸 만한 것은 A에 옮긴다.

## 2. 채점 기준

정할 것: 질문 하나의 결과를 무엇으로 셀지.

| 선택지 | 지표 | 장점 | 단점 |
| --- | --- | --- | --- |
| A. 정답/오답 하나 | 질문마다 맞음·틀림 | 단순하고 읽기 쉬움 | 튀르키예 5개 도시 중 4개처럼 "거의 맞음"이 안 보임. 개선 폭이 묻힘 |
| B. 사실 체크리스트 + 근거 이탈 + 검색 재현율 | 필수 사실 맞힌 비율, 근거 글에 없는 주장 있음/없음, 정답 글이 검색된 비율, 없는 질문에 "없다"고 했는지. 비용·지연·LLM 호출은 같이 기록 | 검색이 문제인지 답변이 문제인지 나눠서 볼 수 있음. 2주차 문제(찾은 장소를 또 찾음)가 재현율로 드러남 | 지표가 4개라 "어느 쪽이 나은가"를 한 숫자로 못 말함 |
| C. 1~5점 루브릭 | 판정자가 점수 하나 | 한 숫자로 비교 | 점수 기준이 흔들리고, 왜 3점인지 추적이 어려움 |

추천: **B**. 대표 숫자 하나가 필요하면 "사실 맞힌 비율 평균"을 쓰고, 근거 이탈은 따로 센다.

## 3. 자동 채점 방법

정할 것: 2번 지표를 무엇이 판정할지.

검색 재현율과 비용·지연·호출 수는 코드로 바로 센다(검색된 post id와 정답 slug 비교). 판정이 필요한 것은 "사실을 맞혔나"와 "근거에 없는 주장이 있나"다.

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| A. LLM 판정자(구조화 출력) | 표현이 달라도 같은 사실을 알아봄("해발 2281m" vs "2,281미터") | 판정 비용이 든다. 판정자 자체가 틀릴 수 있어 사람 채점과 맞춰 봐야 함 |
| B. 키워드·정규식 매칭 | 비용 0, 결정적 | 한국어 표현 변형에 약하고, 근거 이탈은 판정 불가 |
| C. 키워드로 먼저, 못 맞힌 것만 LLM | 비용을 줄임 | 경로가 둘이라 결과를 해석하기 복잡 |

A를 고르면 함께 정할 것:
- 판정자 모델: 답변과 같은 `claude-haiku-5-5`(싸다, 자기 답에 후할 수 있음) / 더 큰 `claude-sonnet-5-5`(비싸다, 편향이 덜함). 정확한 단가는 실행 전에 claude-api 문서로 확인하고 Decimal로 계산한다.
- 검증: 사용자가 답변 10개를 손으로 채점하고 판정자와 일치율을 본다. 낮으면 판정 프롬프트를 고친다.

추천: **A + sonnet 판정자 + 사람 10개 대조**. 판정자가 믿을 만한지 숫자로 남기는 게 이번 주 핵심이다.

## 4. 무엇을 몇 번 돌릴지

정할 것: 비교 대상과 반복 횟수. 2주차에 같은 튀르키예 질문이 3번에 5개 도시 중 4, 4, 3개로 흔들렸다.

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| A. agentic 그래프만, 질문당 1번 | 가장 싸고 빠름 | 한 번의 운으로 결론을 낼 수 있음 |
| B. v0 + agentic, 질문당 3번 | 에이전트가 v0보다 나은지 다시 확인하고 흔들림(최소·최대)도 보임 | 호출이 A의 약 6배. 24문항 × 2 × 3 = 144번 실행 + 판정 |
| C. agentic만, 질문당 3번 | 흔들림은 보이고 B보다 쌈 | v0 대비 이득을 다시 확인하지 못함 |

결과 저장: 실행마다 JSONL 파일(`BE/experiments/week3/results/<날짜>-<버전>.jsonl`)에 남긴다. DB 테이블은 만들지 않는다(필요하면 그때 Alembic으로).

추천: **B**. 기준선을 한 번 제대로 잡아 두면 이후 프롬프트 수정은 agentic만 돌려도 비교할 수 있다. 실행 스크립트에 비용 상한(예: $2)을 두고 넘으면 멈춘다.
