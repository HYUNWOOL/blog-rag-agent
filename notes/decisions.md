# 판단 기록

## 1주차 결정 (2026-10-25, 근거: notes/week1-decision-points.md)
- 스키마: posts(url UNIQUE) + chunks(post_id FK, UNIQUE(post_id, chunk_index)) 2개. 본문 해시가 같으면 재임베딩 안 함.
- 임베딩: 로컬 BAAI/bge-m3, 1024차원, sentence-transformers. API 키·비용 없음 대신 의존성과 모델 다운로드가 큼.
- 청킹: `##` 소제목 단위, 앞에 "글 제목 > 소제목", 이미지 alt·캡션은 남기고 URL은 뺌, 짧은 섹션은 합치고 긴 섹션은 문단 경계에서 자름, 코드 블록은 자르지 않음.
- 인덱스: HNSW(vector_cosine_ops). 1주차 프롬프트에서 지정.
- State: messages(add_messages) + llm_calls. 토큰은 메시지의 usage_metadata에서 합산.
- 상한: 넘으면 실패로 멈춤(raw_loop max_steps=6 예외, LangGraph recursion_limit=10 → GraphRecursionError). 강제 답변 없음.
- 툴 설명: 용도와 언제 쓸지까지 적음(search_posts 먼저, get_post는 청크로 부족할 때만).
- 답변 프롬프트: 블로그 글만 근거로 한국어로 답하고, 근거가 없으면 없다고 말하고, 끝에 참고한 글 제목과 URL. 세 버전 공통.

## 판단: 이 블로그 챗봇에 에이전트가 필요한가?
- 상황: 같은 프롬프트·툴·모델(claude-haiku-5-5, effort low)로 세 버전을 만들었다. v0는 코드가 "검색 1번 → 답 1번"을 정하고, raw_loop·LangGraph는 LLM이 검색어·툴·종료를 정한다. questions.txt 10개(쉬움 3, 중간 4, 어려움 3)로 비교했다(2026-10-25).
- 선택지: A 워크플로우(v0)만 / B 에이전트(LangGraph)만 / C 기본은 v0, 여러 글을 이어야 하는 질문만 에이전트
- 결정: **C** (2026-10-25 확정). 기본은 v0 워크플로우, 여러 글을 이어야 하는 멀티홉 질문만 에이전트로 보낸다. 근거: 10개 중 에이전트가 v0보다 나은 답을 낸 건 멀티홉인 9번 하나였고, 나머지는 비용·지연만 더 들었다. 단, 질문 10개 중 멀티홉 1개라 표본이 작으므로 2주차 평가셋에서 멀티홉 비율을 늘려 다시 확인한다.
- 포기한 것: 단일 경로의 단순함. 질문이 어느 쪽인지 고르는 라우팅(규칙 또는 LLM 분류)이 하나 더 생기고, 경로가 두 개라 테스트·평가도 두 배가 된다. 라우팅 방식은 아직 정하지 않았다.
- 어떻게 확인했나: `experiments/week1/compare.py`로 세 버전을 같은 질문에 돌리고, `compare_answers.md`의 답을 원문에서 확인한 정답(질문별 출처 글·소제목)과 하나씩 대조했다. 비용은 Decimal로 계산(Haiku 5.5 단가: 입력 $0.10/1M, 출력 $0.50/1M, claude-api 스킬 모델표 기준).
- 결과(숫자):

  | 버전 | 평균 LLM 호출 | 평균 입력/출력 토큰 | 질문당 비용 | 평균 지연 | 원문과 맞은 답 |
  | --- | --- | --- | --- | --- | --- |
  | v0 | 1.0 | 3278 / 466 | $0.00056 | 2.7초 | 9/10 (9번 튀르키예 순서 일부만), 4번에 원문에 없는 내용 추가 |
  | raw_loop | 2.1 | 5891 / 658 | $0.00092 | 4.4초 | 10/10, 2번 출처 제목 오타("블로그의 20분") |
  | langgraph | 2.1 | 6269 / 692 | $0.00097 | 5.0초 | 10/10 |

  에이전트는 질문당 비용이 v0의 약 1.6~1.7배, 지연은 +1.7~2.3초. 검색을 더 한 질문은 9번 하나(호출 3회). 10번(블로그에 없는 내용)은 세 버전 모두 "없다"고 답했다.

## 판단: 청크를 어떤 단위로 자를까?
- 상황: 글 33편, 본문 약 10만 6천 자(글당 2.1천~5.2천 자), `##` 소제목 248개, 이미지 353개(전부 alt, 캡션 342개), 코드 블록 0개. 질문은 "어느 장소의 가격·시간·이유"처럼 글 안의 한 부분을 묻는 게 대부분이다.
- 선택지: A 글 1개 = 청크 1개 / B `##` 소제목 단위 / C 고정 길이(예: 800자) + 겹침
- 결정: **B** (2026-10-25). 청크 앞에 "글 제목 > 소제목"을 붙이고, 이미지는 alt만 남기고, 200자 미만 섹션은 합치고 1500자 초과는 문단 경계에서 자르고, 코드 블록은 자르지 않는다.
- 포기한 것: A의 단순함(청크 33개, 규칙 없음), C의 고른 길이와 구현 단순함. 청크 단위 해시로 바뀐 청크만 재임베딩하는 방식도 미뤘다(글 단위 해시로 글 전체를 교체).
- 어떻게 확인했나: 적재 후 청크 길이 분포를 SQL로 확인하고, `experiments/week1/search_questions.py`로 questions.txt의 top-3를 봤다. 청킹 규칙은 `tests/test_chunking.py`(소제목 분리, alt만 남김, 짧은 섹션 합치기, 긴 코드 블록 보존)로 고정했다.
- 결과(숫자): 청크 261개, 평균 497자(최소 233, 최대 1230), 도입부 청크 33개(글마다 1개). 블로그에 답이 있는 단일 글 질문 8개(1~8번)에서 1위가 정답 글 8/8, 정답 소제목 7/8(6번은 같은 글 도입부가 1위, 정답 소제목 "첫날 밤"이 2위). 정답 1위 청크의 거리 0.249~0.462.

## 2주차 결정 (2026-10-31, 근거: notes/week2-decision-points.md, 모두 추천안)
- State: 명시 필드(question, query, chunks, attempts, verdict, answer, llm_calls).
- 충분성 판단: LLM 판정(구조화 출력 {sufficient, missing}). 거리 임계값은 쓰지 않음.
- 재검색: 상한 2번(총 검색 3번), 도달하면 insufficient 노드에서 안내. recursion_limit은 15로 올림.
- rewrite_query: 재검색 때만 돈다. 첫 검색은 질문 그대로.
- 질문 로그: question_logs(PK (thread_id, turn), question, status, answer, attempts, llm_calls, source_post_ids, created_at, updated_at), (thread_id, turn) 기준 멱등 upsert. 두 턴 대화를 위해 "스레드 하나에 질문 하나"를 바꿨다.
- 후속 질문 검색: 대화 기록이 있으면 rewrite_query가 먼저 독립 검색어를 만든다. 첫 턴은 질문 그대로.
- 근거 문서 id: answer 구조화 출력으로 모델이 고른 글만 남기고, 코드에서 이번 턴에 검색된 id로 거른다.
- 체크포인터 테이블: Alembic 규칙의 예외로 두고 전용 스크립트로 setup() 실행.
- 노드: async + AsyncPostgresSaver(노드 timeout을 쓰기 위해).
- 판정 기준: A 완화(핵심에 답할 수 있으면 세부가 빠져도 충분). 질문 6개 재실행 결과는 그대로였다. 튀르키예 순서 질문은 여전히 insufficient이고, 재검색어가 요약 글을 찾느라 안탈리아 구간 청크가 없었다.
- 재검색 프롬프트: 장소·구간 하나만 찾도록 수정. 튀르키예 질문이 3번 모두 answer로 갔지만 5개 도시 중 4, 4, 3개만 답했고, 한 번은 카파도키아 방문 기록이 없다고 틀리게 답했다. 재검색어가 이미 찾은 장소를 다시 찾는 문제가 남았다.
- 흐름 설명: 2주차는 사용자 요청으로 AI가 notes/flow.md 5~7절을 썼다. "내가 흐름을 설명하지 못하면 넘어가지 않는다" 단계를 이번 주만 생략했다.
- 멀티홉 답변 품질: 여기서 튜닝을 멈추고 3주차 평가로 넘긴다. 질문 하나에 프롬프트를 더 맞추지 않고, 멀티홉 질문을 늘린 평가셋으로 판정 기준과 재검색(찾은 글 제목 전달 등)을 다시 정한다.
