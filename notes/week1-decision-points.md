# 1주차 결정 포인트 (미결정)

정하면 `notes/decisions.md`에 한 줄씩 남긴다. API 근거는 `notes/week1-api.md`.

데이터 규모(수집본 기준): 글 33편, 본문 텍스트 약 10만 6천 자(글당 2.1천~5.2천 자, 중앙값 약 3천 자), `##` 소제목 248개(글당 약 7.5개), 이미지 353개(전부 alt 있음, 캡션 342개), 코드 블록 0개.

## 1. posts·chunks 스키마

정할 것: 테이블을 몇 개로 나눌지, 어떤 컬럼을 두는지, 재적재 때 무엇으로 같은 행을 찾는지(유니크 키).

| 선택지 | 내용 | 장점 | 단점 |
| --- | --- | --- | --- |
| A. posts + chunks 2개 | posts(url UNIQUE, title, published_at, updated_at, tags text[], content_hash), chunks(post_id FK, chunk_index, text, embedding, UNIQUE(post_id, chunk_index)) | 글 메타데이터 중복 없음. 글 단위 재적재가 쉬움(content_hash가 같으면 건너뜀) | 검색 결과에 제목·URL을 붙이려면 JOIN 필요 |
| B. chunks 1개(비정규화) | chunk 행마다 url, title, tags를 같이 저장 | 검색 쿼리가 단순. JOIN 없음 | 글 메타데이터가 청크 수만큼 중복. 제목이 바뀌면 여러 행을 고쳐야 함 |
| C. A + chunks에 chunk_hash | A에 청크 텍스트 해시를 추가하고 UNIQUE(post_id, chunk_hash) | 글 일부만 바뀌어도 바뀐 청크만 다시 임베딩 | 청크 순서 관리가 따로 필요. 33편 규모에서는 이득이 작음 |

추천: **A**. 재적재는 "글의 content_hash가 다르면 그 글의 청크를 지우고 다시 넣기"로 충분히 멱등하다. 유니크 키는 posts.url, chunks(post_id, chunk_index).

## 2. 임베딩 모델과 차원

정할 것: API형인지 로컬 모델인지, 어떤 모델과 차원인지. 차원은 `vector(N)` 컬럼 타입에 박히므로 바꾸려면 마이그레이션과 전체 재임베딩이 필요하다.

| 선택지 | 예 | 한국어 품질 | 비용·운영 |
| --- | --- | --- | --- |
| A. API 다국어 모델 | Voyage 다국어 계열, OpenAI text-embedding-3 계열 | 다국어 지원이 공식 명시된 모델이 많다. 우리 데이터로 비교한 적은 없음 | 코퍼스가 약 10만 자라 전체 임베딩 비용은 매우 작다(단가는 각 가격표 확인 필요). 키 하나 추가, 네트워크 필요, 테스트는 가짜 임베더로 대체 |
| B. 로컬 다국어 모델 | BAAI/bge-m3(1024차원), intfloat/multilingual-e5-large(1024차원, `query:`/`passage:` 접두어 필요) | 한국어 포함 다국어 검색 벤치마크에서 많이 쓰임. 우리 데이터로는 미검증 | API 비용 0. 대신 sentence-transformers와 torch 의존성 추가(수 GB), 첫 실행 때 모델 다운로드, CPU에서는 느림 |
| C. 둘 다 작게 비교한 뒤 선택 | 질문 10~20개로 A 하나와 B 하나의 top-k 적중률 비교 | 근거 있는 선택이 됨 | 하루 정도 더 듦. 평가 질문을 먼저 만들어야 함 |

추천: **C를 작게**, 그다음 하나로 고정. 바로 정해야 한다면 운영이 단순한 A. 주의: 모델 이름·차원·단가는 고르기 전에 공식 문서에서 다시 확인한다(이 표는 기억에 기댄 부분이 있다). pgvector `vector` 타입의 HNSW 인덱스는 차원 상한이 있으니(2000으로 알고 있음, 미확인) 3072차원 같은 큰 모델은 차원 축소 옵션이 필요하다.

## 3. 청킹 기준

정할 것: 무엇을 한 덩어리로 자를지, 이미지 alt·캡션을 본문에 넣을지, 겹침(overlap)을 둘지.

| 선택지 | 내용 | 장점 | 단점 |
| --- | --- | --- | --- |
| A. 글 1개 = 청크 1개 | 글 전체를 임베딩 | 가장 단순. 청크 33개 | 3천 자 글 안의 특정 장소·가격 질문에 대한 검색 정밀도가 떨어짐 |
| B. `##` 소제목 단위 | 소제목 하나와 그 아래 본문을 한 청크로. 앞에 글 제목을 붙임 | 블로그 구조와 맞음(소제목이 장소·시간 단위). 청크 약 250개, 평균 400자 안팎 | 아주 짧거나 긴 섹션이 생김. 짧은 건 합치고 긴 건 자르는 규칙이 필요 |
| C. 고정 길이 + overlap | 예: 800자, 겹침 100자 | 길이가 고르다. 구현이 쉬움 | 문장·섹션 중간에서 잘림. 출처를 "어느 소제목"으로 보여 주기 어려움 |

추천: **B**. 청크 텍스트 앞에 `글 제목 > 소제목`을 붙이고, 이미지 alt와 캡션은 본문에 남긴다(사진 설명에 장소 정보가 많다). 이미지 URL은 청크 텍스트에서 빼서 메타데이터로 둔다.

## 4. 인덱스 종류

정할 것: 벡터 인덱스를 HNSW로 할지 IVFFlat으로 할지, 아니면 아직 두지 않을지.

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| A. HNSW | 재현율·속도 균형이 좋음. 데이터가 없어도 미리 만들 수 있음 | 빌드가 느리고 메모리를 더 씀(우리 규모에서는 무시할 수준) |
| B. IVFFlat | 빌드가 빠르고 작음 | 데이터가 들어간 뒤에 만들어야 리스트가 의미 있음. 데이터가 바뀌면 재생성 권장. lists·probes 튜닝 필요 |
| C. 인덱스 없음(정확 검색) | 청크 수백 개면 전체 스캔이 충분히 빠르고 결과가 정확함 | 인덱스 사용법을 배우는 목적에는 안 맞음. 데이터가 커지면 추가 마이그레이션 필요 |

추천: **A(HNSW, vector_cosine_ops)**. 청크 수백 개라 성능 차이는 없지만, 운영에 쓸 형태를 처음부터 익히고 마이그레이션 한 번으로 끝낸다. 정확 검색 결과와 top-k가 같은지 테스트로 한 번 비교해 둔다.
